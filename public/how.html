How it works

A merge queue for swarms of coding agents

A pull request assumes a person on each end: one writes, one reads, and whoever comes second fixes the conflict by hand. agentqueue is built for dozens of agents that arrive all at once and are happy to redo their work. It schedules them around each other before they write, gives every attempt its own repository, reviews each change against what the agent said it would do, and lands everything through a single writer.

The problem

Git workflows assume few writers. Agents bring many.

Point several coding agents at one repository and they collide constantly. Each branches from a slightly different main and edits the same hot files. Each opens a pull request that is out of date by the time anyone looks at it.

41.7%of replayed merges between pull requests from two different AI agents, open in the same repository at the same time, conflicted: 48 of 115 pairs, against 19.8% for pairs from the same agent (Xu et al. 2026, arXiv 2607.04697).

The usual tools make this worse:

Conflicts are found too late

You only learn two agents stepped on each other when the second PR fails to merge, after both have done all their work.

Agents are poor hand-mergers

Asking an agent to resolve conflict markers in code it didn't write is how subtle bugs get in. The tooling assumes a human who understands both sides.

Review doesn't scale

Agents open changes faster than anyone can read them, and a large agent change can be too big for a single model call.

The why gets lost

A merged commit says what changed but not what the agent was asked to do, what it waited on, why it was sent back, or who approved it.

The core idea

Borrow from big monorepos, then use what agents are good at

Large monorepos hit "many writers, one main" first. The pattern behind Rust's bors, OpenStack's Zuul, Uber's SubmitQueue (built for thousands of commits a day) and Meta's pushrebase is always the same: serialize the commit point, schedule everything else around conflicts, and keep each change small and identifiable.

BorsZuulUber SubmitQueueMeta pushrebaseGerrit Change-IdGitLab merge trains

Agents add one twist humans can't offer: re-running them is cheap. A human whose change conflicts has to resolve it by hand. An agent can throw its attempt away and carry out the same intent again on the new main, with a note saying why.

Declare before you write. Redo, don't resolve.
The solution

The life of a task

Every change, from a Workers AI agent, Claude Code or a human, goes through the same six steps. The dashboard shows them as live lanes.

  1. 1ClaimState the intent and the files you'll touch
  2. 2WaitOnly if another live task holds one of those files
  3. 3ForkA fresh repo forked from current main, with its own token
  4. 4ReviewLease check, then a model compares the diff with the intent
  5. 5QueueOne writer merges into main, one task at a time
  6. 6LandOne squashed commit carrying the task's whole story
The redo loop. If review requests changes, the agent edited someone else's files, or the merge still conflicts, the attempt is thrown away. The task is re-forked from the new main and sent back to the agent with the reason. The agent re-executes its intent; nobody hand-merges.
01

Declare before you write: leases

A claim names files or directory prefixes (src/auth.ts, src/). If any of them overlaps a live task's claim, the new task waits, and it is forked from main only after the blocker lands. It starts from code that already includes the other change, so the conflict never happens.

  • Disjoint claims run fully in parallel, each in its own fork.
  • Leases are first come, first served, and waiting tasks count. A big refactor that claims src/ can't be starved by a stream of small changes, and small changes can't slip in under it.
  • Leases are enforced, not advisory. On submit, the coordinator diffs the fork. Editing a file that another live task holds sends the change straight back, before it costs a review.
02

Every attempt gets its own repository

Each attempt is a real Artifacts fork of main with a short-lived, repo-scoped write token. Agents use plain git clone / git push; there's nothing to install and no branch naming convention to follow. An agent can only write to its own fork, never to main. Forks are deleted as soon as the attempt lands, is redone or is abandoned.

03

Review against intent, at any size

Before a change enters the queue, a reviewer model (gpt-oss-120b on Workers AI) reads the unified diff alongside the agent's stated intent and claims. It sends back incomplete work, unrelated edits and obvious bugs.

  • Large changes are split into chunks sized to the model's context and reviewed in parallel against the same intent. Every chunk must pass. In our tests, a 10,000-line refactor reviewed as 8 chunks in about 18 seconds, and 30,000 lines as 22 chunks in about 35.
  • Fail closed, never wedge. If the reviewer gives no usable verdict (after one retry), the change is too big to review in pieces, or review rounds run out, the task is parked for a human and its lease is released. A human can land it with aq approve.
Why this matters: before chunking, a 10k-line change overflowed the model's 128k context. The review crashed and left the task holding its src/ lease forever, blocking every other agent. That exact failure is what makes big agent changes dangerous.
04

One writer for main

Each project has one Durable Object coordinator, the only thing allowed to move main. It keeps a warm, in-memory bare mirror of main (isomorphic-git on an in-memory filesystem) and lands queued tasks one at a time: fetch the fork, three-way merge against current main, write one squashed, single-parent commit and push. Main stays linear, with exactly one commit per task.

05

Redo, don't resolve

If a queued change still conflicts at merge time (for example, it touched lines that a just-landed task also changed), the coordinator evicts it. It forks a fresh attempt from the new main and hands the agent feedback such as "Your change conflicted with work that landed first on src/routes.ts. Redo the intent on top of the new main and keep their changes." The agent re-executes from intent instead of editing conflict markers.

06

The context lives in git

Every landed commit carries the task's story as standard git trailers: what was claimed, whom it waited for, every redo and why, and who reviewed it. Any git client can read it, and it survives clones, mirrors and exports.

$ git log --format='%s%n%w(0,4,4)%(trailers)'

Bring your own agent

Any agent that can run git can join

Workers AI agents are just one kind of client. Claude Code, Codex or a human use the same protocol through the aq CLI, which is plain HTTP plus git:

# declare intent and claims; waits if leased, then clones your fork
aq claim -p my-project -a claude -m "Add a priority badge to formatTodo" src/format.ts
cd aq-<task> && $EDITOR src/format.ts && git commit -am "priority badge"

# push, review, queue, land; re-checks out a fresh fork with feedback if sent back
aq submit .

# human override for a task parked by the reviewer
aq approve -p my-project <task>

The HTTP API (POST /p/:project/tasks, /submit, /abandon, /approve, and live events on /ws) is documented in the README.
